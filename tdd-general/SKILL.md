# 測試驅動開發

TDD 就是紅 → 綠的循環。這份 skill 是讓循環產出「值得留下的測試」的參考：什麼是好測試、測試放在哪裡、反模式，以及循環的規則。每一節在每一輪都適用：在循環開始前與進行中查閱，而不是事後。

探索程式碼時，先找專案既有的詞彙表、需求規格與決策紀錄（若有），讓測試名稱與介面用語符合專案的領域語言，並遵守其中的決定。測試的放置、命名與執行指令，以專案既有慣例（`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、既有測試檔）為準。

## 什麼是好測試

測試透過公開介面驗證行為，而不是驗證實作細節。程式碼可以整個改掉，測試不該跟著改。好的測試讀起來像規格：「批次刪除項目時，重複的 ID 只刪一次」清楚說明系統具備什麼能力；它在重構後依然成立，因為它不在乎內部結構。

範例見 [tests.md](references/tests.md)，替身（mock）使用準則見 [mocking.md](references/mocking.md)。

## 接縫：測試放在哪裡

接縫是你測試的公開邊界：不必伸手進內部就能觀察行為的介面。測試只放在接縫上，絕不針對內部實作。

只在事先講好的接縫上測試。寫任何測試之前，先列出要測的接縫，並與使用者確認。未經確認的接縫一律不寫測試。例外：接縫已由工單或規格指定，或已由呼叫本 skill 的一方確認時，不必再問使用者，直接沿用。你不可能測遍所有東西，事先談好接縫，測試力氣才會花在關鍵路徑與複雜邏輯上，而不是每個邊角情況。

詢問：「公開介面是什麼？我們要測哪些接縫？」每個提議的接縫附一行說明：它抓得到什麼、抓不到什麼。

常見的接縫與測試方式（依專案實際使用的框架替換）：

| 範圍 | 接縫 | 測試方式 |
| --- | --- | --- |
| 後端業務流程 | 對外 API | 整合／驗收測試：啟動應用程式，以 HTTP 呼叫 API，驗證回應與可觀察的結果；資料庫用測試專用資料庫（如 Testcontainers），外部系統用替身伺服器 |
| 後端純邏輯 | 純函式、值物件 | 單元測試（JUnit、xUnit、pytest 等） |
| 前端 | hook、純函式、API client | 元件／單元測試（Vitest、Jest、Testing Library 等） |

循環中只跑本次變更相關的測試（指定測試類別、檔案或 tag）；完整測試套件交給 CI。

業務分支優先從 API 接縫覆蓋，不要為了覆蓋率去替身自己的 repository 或 service 寫隔離式單元測試。

當介面本身的形狀有疑問時（模組多深、接縫該放哪、介面該暴露什麼），先和使用者討論介面設計，再開始寫測試。

## 反模式

- 與實作耦合：替身取代內部協作者、測試私有方法，或經由旁路驗證（例如自寫測試程式直接下 SQL 查表，而不是透過介面讀回）。辨識方式：重構後行為沒變，測試卻壞了。
- 套套邏輯：斷言用程式碼的同一套算法重算預期值（`expect(add(a, b)).toBe(a + b)`、用相同方式手工推導出的快照、拿常數和自己比較），所以它天生會通過，永遠不可能與程式碼意見不同。預期值必須來自獨立的事實來源：已知正確的字面值、推導過的實例、規格。
- 水平切片：先把所有測試寫完，再寫所有實作。整批寫出的測試驗證的是想像中的行為：你測的是東西的形狀，而不是使用者面對的行為，測試會對真正的變化變得不敏感，而且你在理解實作之前就先綁死了測試結構。改用垂直切片：一個測試 → 一段實作 → 重複，每個測試都是一發曳光彈，依上一輪學到的東西調整。

## 循環的規則

- 先紅再綠。先寫會失敗的測試，再寫剛好能讓它通過的程式碼。不要預想未來的測試，也不要加推測性的功能。
- 確認紅燈的原因：測試必須是因為「行為尚未實作」而失敗，不是語法、匯入或設定錯誤。
- 一次一個切片。每一輪只有一個接縫、一個測試、一份最小實作。
- 重構不屬於這個循環。重構放在測試全綠後的審查階段，不在紅 → 綠的實作循環裡。

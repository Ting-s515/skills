# Handoff 交接文件

把「目前對話」整理成一份獨立可讀的交接 Markdown。接手的 agent 沒看過這段對話，只讀這份文件就要能接著做。
重點是**接手需要的資訊**，不是對話紀錄：不要貼對話原文，不要寫流水帳。

## 輸出位置

1. 使用者有指定路徑（`$1`）就寫到該路徑。
2. 沒指定時寫到 `.scratch/handoff/<yyyyMMdd-HHmm>-handoff.md`（相對於專案根目錄；不在 git 專案內則用目前目錄）。
   - 先確認 `.scratch/` 已列入 `.gitignore`；沒有就提醒使用者，不要自行修改 `.gitignore`，也不要把交接文件加入 commit。
3. 以 UTF-8、LF 寫入，內容以繁體中文撰寫。

## 蒐集資訊（唯讀）

交接文件的事實要來自實際狀態，不是記憶。寫入前先用唯讀指令確認：

- `git branch --show-current`、`git status --short`、`git log --oneline -10`：分支、未提交變更、近期 commit。
- 需要時用 `git diff --stat` 看變更範圍。
- 本次對話中跑過的測試或 build 指令與結果：以對話中實際看到的輸出為準。
- 不在 git 專案內時略過 git 區塊，並在文件寫明「非 git 專案」。

不可為了蒐集資訊而執行會改變狀態的指令（commit、安裝套件、改檔案等）。

## 文件結構

依下列順序撰寫，沒有內容的區塊整段省略，不要留空標題：

```markdown
# Handoff：<一句話任務名稱>

> 產生時間：YYYY-MM-DD HH:mm
> 專案路徑：<相對或絕對路徑>
> Git：<分支> @ <短 hash>（未提交變更：N 個檔案／無）

## 接手提示

<可直接貼給接手 agent 的 2–4 行指示：先讀本文件、第一步做什麼、做完怎麼驗證>

## 1. 目標與背景

- 使用者要解決什麼問題、為什麼（2–5 句）
- 使用者的關鍵原話（只引用會影響判斷的，逐字、加引號）

## 2. 目前狀態

- ✅ 已完成：<項目>（證據：commit hash、測試輸出、檔案路徑）
- 🔄 進行中：<項目>（做到哪、卡在哪）
- ⏳ 待處理：<項目>

## 3. 決策與原因

| 決策 | 原因 | 被否決的方案 |
| --- | --- | --- |

## 4. 使用者偏好與限制

- 使用者明確要求或禁止的事（語言、格式、不要做什麼、哪些動作需先確認）
- 專案規則（例如 commit 規範、build 流程）與已知的環境限制

## 5. 重要檔案

- `相對/路徑` — 角色（新增／修改／刪除／重要參考）與一行說明

## 6. 驗證與執行方式

- 如何建置、測試、啟動（完整指令放 code block，註明在哪個 shell／目錄執行）
- 目前已知結果：哪些通過、哪些失敗、哪些沒跑過

## 7. 問題與陷阱

| 問題 | 原因或處理 |
| --- | --- |

## 8. 未解事項

- 待使用者決定的事、尚未查證的假設、已知風險

## 9. 下一步

1. 具體、可立即執行的第一步
2. 之後的步驟
```

## 撰寫規則

- **區分已驗證與未驗證**：親眼看到結果的才寫成事實；推測、記憶、他人轉述標註「未驗證」，放在「未解事項」。
- **誠實記錄失敗**：失敗的測試、跳過的步驟、沒做完的事都要寫，不可寫成已完成。
- **寫「為什麼」**：決策、被否決的方案與原因要留，避免接手者重走死路。
- **使用者偏好必寫**：接手者最容易踩到的是使用者已經講過的規則，第 4 節不可省略。
- **路徑用相對路徑**（相對專案根目錄）；指令與程式碼放 code block，保留原始縮排。
- **精簡**：以接手需要為準，目標在 200 行內；細節用檔案路徑或 commit hash 指過去，不要貼大段程式碼或對話。
- **不放機密**：token、密碼、金鑰、個人電子郵件與其他個資一律不寫；需要時只寫「需要某憑證，由使用者提供」。
- **不要寫本 skill 自己的執行過程**，也不要把「產生交接文件」列為已完成工作。

## 執行步驟

1. 回顧整段對話，列出目標、決策、使用者偏好、已做與未做的事。
2. 用唯讀 git 指令確認分支、未提交變更與近期 commit。
3. 對照上方結構撰寫，沒有內容的區塊省略。
4. 檢查：沒有機密、事實都有來源、第一步具體可執行、長度合理。
5. 寫入輸出位置，回覆檔案的完整路徑，並用 3–5 行說明文件涵蓋的重點與標註為「未驗證」的項目。

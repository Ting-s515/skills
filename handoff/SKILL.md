# Handoff 交接文件

把目前對話整理成一份簡短的交接 Markdown，讓沒看過對話的 agent 讀完就能接手。只寫接手需要的資訊，不貼對話原文。

## 輸出位置

- 使用者有指定路徑（`$1`）就寫到該路徑。
- 沒指定就寫到 `.scratch/handoff/<yyyyMMdd-HHmm>-handoff.md`（專案根目錄；非 git 專案用目前目錄）。
- 在 git 專案內，先用 `git check-ignore .scratch` 確認已被忽略；沒有就在 `.gitignore` 結尾追加一行 `.scratch/`
  （檔案不存在就建立；結尾沒有換行時先補換行），並單獨提交 `.gitignore`。交接文件本身不 commit。
- UTF-8、LF、繁體中文。

## 內容

用唯讀指令確認事實：`git branch --show-current`、`git status --short`、`git log --oneline -10`。
依下列章節撰寫，沒有內容的章節省略：

```markdown
# Handoff：<一句話任務>

> 時間：YYYY-MM-DD HH:mm ｜ 專案：<路徑> ｜ Git：<分支> @ <hash>（未提交變更：N 個／無）

## 目標與背景
使用者要解決什麼、為什麼（2–5 句），必要時引用會影響判斷的原話。

## 目前狀態
- ✅ 已完成：<項目>（附 commit hash 或證據）
- 🔄 進行中：<項目>（做到哪、卡在哪）
- ⏳ 待處理：<項目>

## 決策與使用者偏好
- 決策：<做了什麼>，因為<原因>（被否決的方案一併寫）
- 使用者規則：<語言、格式、禁止事項、commit 規範、需先確認的動作>

## 重要檔案與指令
- `相對/路徑` — 新增／修改／重要參考，一行說明
- 測試、建置或驗證指令（放 code block，註明 shell 與目錄）

## 未解事項與陷阱
- 待使用者決定的事、**未驗證**的假設、已知問題與處理方式

## 下一步
1. 具體、可立即執行的第一步（目前無待辦就寫「等待使用者指示」）
```

## 規則

- 事實要有來源：只寫親眼看到的結果；推測或沒驗證的標註「未驗證」。失敗與沒做完的事如實寫，不可寫成已完成。
- 使用者偏好必寫，接手者最容易踩到使用者已經說過的規則。
- 精簡，目標 100 行內；細節用檔案路徑或 commit hash 指過去，不貼大段程式碼。
- commit 要附 hash、依時間順序列出；提到數量就把項目列全，不用「等」省略。
- 不放機密（token、密碼、金鑰、電子郵件等個資）。
- 不寫本 skill 自己的執行過程。

寫完後回覆檔案完整路徑，並用 2–3 行說明重點與標註為「未驗證」的項目。
